# 使用方式

三個 skills 安裝為同一 skills 父目錄下的相鄰目錄。將本文件的 `<office>` 換成本 skill 的實際絕對路徑，`<project>` 換成使用者指定 startup folder；不要把示例 placeholder 當 shell 原文執行。CLI 詳細欄位以 contracts/runtime-contract.json（執行資料契約）為準。

唯一正式來源是專案根目錄的 startup-cami.yaml（共用正式資料）。先依[核心問答與舊題模式](核心問答與舊題模式.md)確認目前內容與可用流程；下列note／draft／evaluate-input／accept命令只適用舊題模式，核心編輯稿使用本文件末尾的明確回填入口。使用者直接填 questions 裡的 answer；accepted_version 與 history 保留先前已接受版本，不手動改成通過。每次寫入前重讀 inspect 取得最新檔案 hash；只改 YAML 排版不會讓內容評估失效，但會使舊的寫入 hash 失效，必須重讀，避免覆蓋編輯器剛存的內容。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" init --title "我的創業專案"
uv run "<office>/scripts/startup_cami.py" --project "<project>" inspect
uv run "<office>/scripts/startup_cami.py" --project "<project>" validate
```

使用者已直接在 YAML 填好 answer 時，office 先讀這份已保存的完整答案。若尚無相符筆記，把該文字原樣作為 note 的輸入，帶本題 `--question`，再以同一筆記執行 draft 連結；相同正文不改字、不新增一份答案歷史，接著建立 evaluate-input。這不是要求使用者再填一張表，也不能替使用者重寫他已填好的 answer。

在當前對話內讀取完整回答，依「專案與恢復判準」按案例寫成繁體中文或英文訪談筆記。對照來訊檢查資訊與複雜度，確認數字、工程限制、因果、假設與預期結果都有落點。只將整理稿寫成 UTF-8 輸入檔。不要把原話交給 CLI、暫存檔、草稿或評估紀錄。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" note --turn-id "<來訊識別>" --text-file "<整理稿檔>" --expected-revision "<目前版本>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
```

已可對題時，在 note 命令加一次或多次 `--question "<question-id>"` 連結相應題目；這項關聯不需 draft 或 pass，也不增加完成題數。尚未對題時省略參數，仍能從畫布的訪談筆記入口讀取。用 inspect 的 notes 查核筆記識別，evaluate-input 的 note_turns 會提供整理稿 text 及選用的筆記 excerpt。語言檢查無法代替對語意覆蓋的核對。

用 inspect 取得目前 revision 與 source_sha256（整份 YAML 的位元組 hash）；同一來訊重試沿用識別，衝突先重新 inspect 或依 pending transaction 狀態 recover。成功寫入並重讀後，才可說筆記已保存。針對 catalog 的原題引用整份筆記，或加 `--text-file "<整理稿逐段節錄檔>"` 引用其中連續段落。尚未對題、延後或停止時，仍保留已整理筆記；只有已接受答案增加畫布進度。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" draft --question "<question-id>" --turn-id "<來訊識別>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" evaluate-input --question "<question-id>" --kind hypothesis --expected-source-sha256 "<inspect 回傳的 source_sha256>"
```

evaluate-input 的 JSON 輸出是 evaluator 唯一評估 packet；不能手填 hash。若引用其他已存答案，用 --dependency 明示。改寫候選先讓使用者確認再用 --candidate-file 與 --confirmed；沒有改寫不必多問一次。

依回傳 packet 與 runtime contract 由 evaluate 產生 evaluation JSON，再用 inspect 的當前 revision 接受。不要把 下列範例當有效 evaluation，也不手填所有分數為滿分。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" accept --evaluation "<evaluation.json>" --expected-revision "<目前版本>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" render --template-bundle "<模板目錄>"
```

失敗時依 JSON error 判斷；unknown/pending transaction 先 recover。缺 template 不阻斷 YAML 保存。獨立 HTML 不會自動讀取磁碟變動：每次正式資料更新後重跑 render，再重新開啟或 refresh 頁面。本地 Next app 啟動時會自動重新 render 並更新閱讀畫面。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" recover
```

init 從完整 YAML template 複製固定題庫與規則。續跑時讀專案 YAML 的 questions、各題 requirements、canvas 與 rules.rubric；skill assets 只是啟動材料，不是覆蓋專案的第二來源。不要修改固定規則以迴避評估。

## 安裝與依賴

將 startup-cami-office（流程組織）、startup-cami-facilitation（單題引導）、startup-cami-evaluate（回答評估）三個目錄放到 AI host 的同一 skills 目錄，維持相鄰且同版本；不用安裝 gstack。安裝後由 AI host 載入 skill，Python CLI 本身不提供聊天模型。

Python 至少 3.11；uv 依 scripts/startup_cami.py 內 PEP 723 宣告取得固定版本依賴。首次準備環境通常需要網路；要在斷網環境執行，事先在相同環境下載並驗證依賴。唯讀 HTML 可離線開啟，不代表 AI host 或首次依賴安裝離線可用。

未通過的評估也應保存，再依使用者決定延後或續跑：

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" record-evaluation --evaluation "<evaluation.json>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" session-action --question "<question-id>" --action defer --reason "先取得訪談資料" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" session-action --question "<question-id>" --action resume --reason "已補資料" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
```

## 本地 hot reload

首次與續跑詳見 [本地 Next setup](本地Next-setup.md)。使用 `uv run <skill>/scripts/setup.py --project <root> --app-dir <使用者指定位置>` 安裝，Next app 讀既有 renderer，仍以 YAML 為正式來源。

## 決策判斷與獨立複核

先讀 [決策判斷與誠實回答](決策判斷與誠實回答.md)，再依 runtime contract 建立 JSON，不手填假的審查。一般候選可使用 single；關鍵或邊界在首次評估前指定 independent。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" evaluate-input --question "<question-id>" --kind hypothesis --review-policy independent --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" record-evaluation --evaluation "<第一位獨立結果.json>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" record-evaluation --evaluation "<第二位盲審結果.json>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" record-review --review "<比較理由與結果.json>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
uv run "<office>/scripts/startup_cami.py" --project "<project>" record-decision --assessment "<當前決策判斷.json>" --expected-source-sha256 "<inspect 回傳的 source_sha256>"
```

第二份是實際隔離 evaluator 對同 packet 的結果，不是把第一份改名。審查 JSON 的 resolution 依實況 agreed／unresolved／unavailable；independent 只有兩份 pass 且符合最新 agreed review 才可 accept。事後發現邊界時重新建立 independent packet，兩份評估都重取，不重用舊 single pass。

決策 assessment 與正式評分分開；例如公司目的回答已清楚，投資決策仍可 not_ready。先以 inspect 取得當前 revision，再依既有 accept 命令接受；review 或 assessment 本身不寫正式答案。

若在 accept 前保存 assessment，接受造成來源版本改變後該紀錄可成為 stale；要呈現接受後現況，依提交 receipt 用新的 assessment_id 再記一次。舊紀錄保留在共用 YAML，不改寫其時間或來源。single 初評後才發現邊界可以直接升級 independent；不偽造使用者新話，也不能降級略過複核。

### 在對話前標示下一個未完成問題

以 inspect 取得當前 revision，透過 `set-next --question <題庫中的原題識別> --expected-revision <revision> --expected-source-sha256 <source_sha256>` 更新正式 YAML。確認成功再顯示英文原題與情境追問。恢復時優先使用已標示且尚未完成的原題，沒有標示時才由題庫順序提供預設。回看舊題只移動畫布，不改這個標示。


## Canvas headlines

Headlines的單一寫法規範在[Headlines撰寫與核對](../rules/Headlines撰寫與核對.md)，固定雙語骨架及寫法見[headlines骨架](../templates/headlines.md)與[headlines範例](../templates/headlines.example.md)。長度與數量是閱讀建議，不作語意刪減或評分門檻；程式只設每條1000總字元等格式保護。空陣列代表刻意沒有可貼的實際資訊，完整答案保留。

舊題模式保留原key_points欄位與命令名稱，只有一組items；按該正式／待評估正文語言提取一組headlines，不把中英兩組混進同一array，也不假設畫面語言切換會翻譯原答案。雙語骨架只選相符的寫法。正文note／draft或accept更新後，執行key-points-input取得source_sha256及entries；每項帶question_id、role（formal／pending）、source_sha256及完整text。AI依正文提取headlines，以points字串陣列取代text，保留其他欄位，再用set-key-points --file保存。formal／pending分開核對；來源hash不符就重讀，不能強蓋。Headline不增加完成題數，不改正文、scores或accepted版本。

核心模式直接在編輯稿的中英文Headlines區塊按相同規範整理，再使用sync_core.py回填；不呼叫舊key-points命令。沒有可貼資訊時保留區塊標題、下方留空，不放「尚缺資料」占位。兩個語言的便條紙數量與順序對齊，忠實程度仍須AI對正文核對。

大量補齊或改寫時，獨立review核對主張強度、數字、條件、中英配對及使用者口吻；畫面依[Canvas驗收](Canvas驗收.md)實測。不要把Python接受某個長度當成文字品質通過。

## 舊專案遷移

先執行只讀檢查，確認題庫、原答案、筆記、key points、評估與接受狀態完整保留，再進行切換：

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" migrate-yaml
uv run "<office>/scripts/startup_cami.py" --project "<project>" migrate-yaml --apply
```

切換會保留一次性的回復備份，移出原來可填寫位置的 Markdown 與舊領域 sidecars。正常讀寫只使用 startup-cami.yaml（共用正式資料）；舊版紀錄在 YAML 內保留原有內容與 hash，不重新打分。已在 YAML 新增或修改內容後，不可直接拿遷移前備份覆蓋；回復命令必須拒絕這種操作，先保全新增內容。

## 改名前建立的專案（startup101.yaml）

改名前 init 的專案只有 `startup101.yaml`，機器狀態在 `.startup101/`。專案根目錄沒有 `startup-cami.yaml`、只有 `startup101.yaml` 時，startup_cami.py、sync_core.py、setup.py 與本地 Next app 都直接讀寫這份舊檔，pending transaction、寫入鎖與 view.json 繼續放在 `.startup101/`，不需要先遷移。inspect 會回傳 `document` 與 `legacy_document_name`，可確認目前讀的是哪一份。兩個檔案同時存在時，所有命令拒絕執行、不改任何檔案，先保留唯一正式來源。

要改成新檔名時，先預覽再明確套用：

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" migrate-name
uv run "<office>/scripts/startup_cami.py" --project "<project>" migrate-name --apply
```

套用時在兩個寫入鎖下把 YAML 位元組原樣發布為 `startup-cami.yaml`（不覆蓋既有檔），複製 `.startup101/view.json` 到 `.startup-cami/view.json`，再把舊檔移到 `.startup-cami/recovery/name-migration-*/startup101.yaml` 保存，不刪除；`.startup101/` 原樣保留。有 pending transaction 時先 recover。過程中斷而兩個檔案內容相同時，重跑 `migrate-name --apply` 會完成同一次移動；內容不同時拒絕執行。改名後已安裝的本地 Next app 要用 `setup.py --upgrade` 升級，舊版 app 只認得 `startup101.yaml`。

## 20個核心問題的 Markdown 回填

專案已有明確的核心問題編輯稿與原題對應檔時，使用 scripts/sync_core.py（核心問答同步）將中英文 headlines、完整 answers、換句話問及追問存入同一 YAML 的 core_canvas。這是既有編輯稿的明確回填入口，與 migrate-yaml 的舊格式遷移分開；不把20題逐一套回351題。

```sh
uv run "<office>/scripts/startup_cami.py" --project "<project>" inspect
uv run "<office>/scripts/sync_core.py" --project "<project>" --markdown "<核心問題編輯稿.md>" --mapping "<原題對應.mapping.json>" --expected-source-sha256 "<inspect回傳的source_sha256>"
```

預設只預覽，核對分類、題數及來源後加 --apply 才寫入。新核心專案可保留所有題目與欄位標題，將中英文答案及 headlines 內容留空。逐題補齊雙語答案後同步。空白稿不得清除 YAML 內已保存的答案。寫入鎖、來源 hash、原子保存沿用共用資料規則；相同輸入重跑不新增版本，有修改時保留核心歷史。不完整、來源對應錯誤或期間有其他 YAML 修改時拒絕覆蓋；核心內容若曾在 YAML 另改，先整合內容再重新同步。

core_canvas 啟用時，Canvas 與 inspect 使用核心問題的「已填」數量，不使用舊351題的通過數。原題、評估與筆記保留；匯入不產生新分數，也不把舊 pass 套給合併後的回答。此版不提供核心問題的自動 accept；不得透過舊題評估命令假裝更新核心答案。使用者要修改時，更新核心編輯稿再明確同步；Canvas 仍只讀 YAML。

已有本地 Next app 時，依 setup reference 升級已安裝的 runtime 與 template，再以 validate、render 及中英文畫面核對。只改 Markdown 不會自動覆蓋 YAML。

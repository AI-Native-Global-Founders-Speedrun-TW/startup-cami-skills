# Rule 1 - Headlines 是可獨立理解的具體主張

- Level: `MUST`
- Headlines 是畫布便條紙上的內容，從當前完整 answer 提取；一條表達一個可理解的主張。需要一起讀才成立的因果、取捨或條件可以留在同一條，不為拆短破壞意思。
- 讀者不先開完整答案，也應看得懂對象、場景與動作，以及本條要說的結果或差異；不是要求每句都硬填一套欄位。只寫「AI 協調」「集體智慧」等抽象詞不夠。
- 不截取答案前幾字、不按來源子題逐一製作便條紙；相同主張只留一次。核心問題的換句話問與追問共用同一份 answer，不各產生一組重複 headlines。

## Good Example

以下是通用產品表達的寫法示例，不是其他專案的事實。

```text
每個人的 terminal 裡，都有一個 AI-native war room；繼續用自己的 AI，也能一起做決定。
```

## Bad Example

抽象標籤沒有交代在哪裡、誰做什麼。

```text
AI-native war room
高效協作
```

# Rule 2 - 長度與數量依意思調整

- Level: `SHOULD`
- 中文常見長度以30–65個總字元為參考，包含英數、空格與標點；英文常見長度以15–30詞為參考。這是目前已確認寫法的建議範圍，不是拒絕保存、強制補長或影響 scoring 的門檻。
- 更短且已能單獨理解的句子可以保留；較長但需要保留對象、條件、數字或因果時也可以保留。過長先判斷是否包含兩個可獨立成立的主張，再決定拆分；不能直接截字、刪限定或縮小字體來湊長度。
- 每題通常3–6條，有多少實際資訊就呈現多少，不是配額；20個核心問題整併多項資訊時可更多。不要為湊數製作重複句，也不要為限制條數漏掉重要主張。

## Good Example

短句已交代位置，可以保留，不補成完整長句。

```text
An AI-native war room. In everyone's terminal.
```

## Bad Example

為了壓回舊字數限制而刪去使用者要保留的具體資訊。

```text
原句：每個人的 terminal 裡，都有一個 AI-native war room；繼續用自己的 AI，也能一起做決定。
壓成：AI 戰情室
```

# Rule 3 - 使用使用者口吻與已確認用詞

- Level: `MUST`
- 產品、團隊與自己的選擇，以使用者本人會講的話表達；不加「建議創辦人」「該公司應該」等第三人稱旁白。描述其他人或組織的已知行為時保留正確主詞，不把別人的行為改成自己做過。
- 沿用使用者已確認的詞、產品名與句子；重新生成時先讀目前完整答案及現有 headlines。使用者親改的表達與排序不因 AI 覺得更順而默默替換。
- 句子只放主張與必要理由；來源路徑、何時被 AI 確認、改寫理由及評估旁白不寫進便條紙。會改變主張的實際日期、對象、數量與條件仍保留。
- 英文優先用簡單、容易記住與說出口的字，可用短句，不為完整句型增加 buffering words。英文文法修改與 headlines 生成分開；沒有要求修文法時，不擅自重寫使用者已確認的英文。

## Good Example

保留使用者已確認的直接說法。

```text
Everyone explains what they want.
```

## Bad Example

改成 AI 對創辦人的評論，並換掉已確認的簡單用詞。

```text
建議創辦人鼓勵各方充分陳述立場。
Stakeholders articulate their respective desiderata.
```

# Rule 4 - 核心中英文配對，舊題依正文語言

- Level: `MUST`
- 核心模式同題的中英文headlines逐條對應，主張、對象、條件、數字與順序一致；不是逐字翻譯，也不要求兩種語言一樣長。使用者明確要求重排時，兩種語言一起同步。
- 舊題模式的key_points只有一組items，依該formal／pending完整正文的語言保存；雙語骨架只取相符的一種寫法，不將兩組中英內容混入同一items、不新增假locale欄位，也不宣稱切換畫面語言就會翻譯舊題答案或headlines。
- 核心翻譯不加上新能力、證據、承諾、客群或更強結論；不為自然英文刪掉中文的限制。專有名詞與人名可保留原文，不因英文內出現漢字就按中文長度處理。
- 先保持使用者要說的意思，再選簡單自然的英文；若最新一種語言與另一種語言有出入，指出差異、依已確認的修改同步，不自行把舊版當正確答案。

## Good Example

以下配對示範相同動作與時序，不可直接當其他專案事實。

```text
中文：人採納 Plan 後同步決定與理由，讓下一次規劃能接續。
English：After people adopt a Plan, sync the decisions and reasons so later planning can build on them.
```

## Bad Example

英文增加了中文與完整答案沒有支持的結果。

```text
中文：人採納 Plan 後同步決定與理由，讓下一次規劃能接續。
English：AI automatically makes every decision and guarantees a better outcome.
```

# Rule 5 - 只貼已有資訊，保留主張強度

- Level: `MUST`
- 事實、觀察、產品構想、計畫與目標都可以成為 headlines，但不能改變其性質。目標用使用者原來的目標說法，不加「仍是願景」的旁白；也不能把想達到的成效寫成已達成的實績。
- 純「缺少角色」「影響未盤清」「還沒有資料」或評估 blocker 不單獨做便條紙。整題只有缺漏資訊時保存空陣列 `[]`，不塞占位句、不為湊數補造內容；核心 Markdown 的 Headlines 區塊保留標題、清空條列，再由同步命令轉成空陣列。
- 有具體方案、觀察或行動時，可以保留對其意思有影響的未知與條件。例如已有測試方案但未執行，不能改成測試已完成；已知零收入是實際業務狀態，不等同於純「缺資料」。
- 不為讓語氣更肯定而刪掉否定、適用範圍或計畫性質。條件需要留在句子時，用直接說法，不重複加「目前仍可能」「建議再確認」等旁白。

## Good Example

缺漏不製作便條紙；具體但未執行的行動如實寫成計畫。

```text
只有「缺少資料」：[]
已選測試但尚未執行：我們會用一個真實 Plan，比較兩種做法形成方案的時間與結果。
```

## Bad Example

第一句把缺漏變成便條紙；第二句把計畫寫成實績。

```text
角色與影響尚未盤清。
我們已用真實 Plan 證明產品讓所有團隊更快形成更好的方案。
```

# Rule 6 - Headlines 不代替正文、評分或閱讀驗收

- Level: `MUST`
- 完整 answer 是引導與評估的對象；headlines 只是其閱讀層，不單獨加分，也不因生成便條紙增加完成數。不以短句代替完整答案交給 evaluator；headline 的字數或畫面好看程度不改 scoring。
- 有效狀態仍依目前資料流程判定：核心匯入為已填／saved，不因已有 headlines 成為已通過；舊模式的正式與待評估內容分開，來源不符的舊 headlines 不沿用。
- 同一題所有 headlines 都呈現在畫布，依數量展開白色問題 container，不設四條顯示上限；完整答案閱讀區也保留全部內容。已有人工排序就是呈現順序，不自行以長度排序或將中文與英文各排一套。
- 畫布以白色 question container 包住問題及長方形便條紙，完整答案點開閱讀；桌面與手機都要能讀懂。文字較長時以寬度、換行與單欄適應，不裁字、不把便條紙隱藏到看不見、不擠成狹長矩形，也不縮字到難讀。

## Good Example

```text
來源有五條 headlines：畫布依既有順序呈現全部五條，白色問題 container 隨內容展開；完整答案閱讀區也保留全部五條。
核心答案已保存：顯示已填，不宣稱評估通過。
```

## Bad Example

```text
便條紙寫得有力，所以把完整答案評為通過。
為了讓四條都擠進固定卡片，刪掉第五條並將字體縮小到看不清楚。
```
